Core Concepts

Every multiagentz stack is a tree of four agent types. Understanding these four building blocks is all you need to design your own system.

LeadAgent — The Brain

The top-level orchestrator. There is exactly one LeadAgent per stack. It receives every user question, classifies it, routes it to the right coordinator group(s), and synthesizes the final response. It also manages orchestration modes (standard, consensus, perspective), caching, and conversation memory.

In the YAML config, the lead section defines which model powers the LeadAgent. This should be your most capable model — it makes the routing decisions that determine everything downstream.

CoordinatorAgent — The Group Manager

A CoordinatorAgent owns a team of sub-agents. It receives questions from the LeadAgent, routes them to the right sub-agent(s) within its group, runs queries in parallel, and synthesizes multi-agent responses before sending them back up.

Coordinators also manage cross-pollination: when a routed agent has a twin, the coordinator automatically triggers the A/B debate loop instead of a simple single-agent query. Think of coordinators as department managers who know their team's specialties.

SubAgent — The Worker

The leaf node. A SubAgent points at a specific repository path, reads source files from it, and answers questions using an LLM with that context. Each SubAgent has its own model, provider, description, and list of key_files that define what it can see.

The key_files list is critical: it determines what context the agent has. An agent that only sees routes/ will reason differently than one that sees core/. This deliberate scoping is what makes multi-agent analysis powerful.

Twin Pairs — A/B Cross-Pollination

The secret weapon. Two sub-agents with different models analyze the same question, swap their outputs, refine their answers incorporating the counterpart's perspective, then a coordinator reconciles the two refined outputs into a single authoritative answer.

Why it works
Using different models (e.g., Opus vs Grok) ensures genuine cognitive diversity — different reasoning architectures, not just different random seeds. Each model has different blind spots. The debate process surfaces errors that either model alone would miss.

Orchestration Modes

standard

Simple routing. LeadAgent classifies the question, routes to the right coordinator(s), gets answers, synthesizes. Fast and cost-effective. Good for straightforward questions.

consensus

Iterative conflict resolution. Routes to multiple agents, identifies contradictions between their responses, generates refinement questions, re-queries until agreement or max iterations. Good for ambiguous technical questions.

perspective

Full multi-phase orchestration. Each coordinator group becomes an independent perspective that bootstraps context, generates a solution, receives LEAD feedback, refines iteratively, then all perspectives are synthesized. Best for complex design tasks.

The Perspective Orchestration Pipeline

When orchestration mode is set to perspective, every question triggers the full 4-phase pipeline. Each coordinator group operates as an independent perspective, and the LEAD synthesizes their work into a unified output.

Phase 1
Bootstrap Q&A Alignment
Each perspective agent asks clarifying questions about the task. The LeadAgent answers using its full routing capability (querying other agents as needed). This continues up to 10 Q&A turns until the perspective signals "ALIGNED" — meaning it has enough context to generate an independent solution.

The YAML Configuration

The YAML file is the only thing you edit. It defines your entire agent stack: which models to use, how to organize them, what files they see, and how they debate. Every field is explained below.

One file, complete control
You do not write any Python code. The YAML config declares everything. The framework reads it and builds the agent tree automatically.
stack.yaml -- Top-level fields
name: my-analysis-stack           # Human-readable stack name

orchestration:
  mode: perspective               # standard | consensus | perspective
  max_iterations: 5              # Refinement cycles before stopping
  cross_pollination: true        # Enable A/B twin debate loops
  • name — Shows up in terminal output, logs, and exported HTML files.
  • orchestration.mode — Choose standard for simple routing, consensus for iterative conflict resolution, or perspective for the full 4-phase pipeline.
  • max_iterations — How many refinement rounds before the system stops. Higher = better quality but more expensive. Start with 3–5.
  • cross_pollination — When true, any agent with a twin field will automatically trigger the A/B debate loop.
stack.yaml -- lead section
lead:
  model: claude-opus-4-6            # The model powering your LeadAgent
  provider: anthropic              # anthropic, openai, xai, google, etc.

  routing_prompt_extra: |
    Description of your system and how to route questions.
    Which coordinator handles what. Cross-cutting rules.
    This is the most important text in your entire config.

  keywords:                         # Fast pre-route hints (before LLM)
    coordinator_a:
      - sdk
      - client
      - library
    coordinator_b:
      - backend
      - server
      - api
  • model + provider — Use your strongest model here. The Lead makes routing decisions that determine everything downstream.
  • routing_prompt_extra — Free-form text injected into the routing classifier prompt. Describe what each coordinator group handles and any cross-cutting rules. This is the single most important thing to get right.
  • keywords — Fast keyword matching that bypasses the LLM entirely. If a question contains "sdk", it routes directly to coordinator_a without an LLM call. Saves time and money for obvious routing.
stack.yaml -- agents section (nested inside lead)
  agents:
    my_group:                       # Coordinator group name
      type: coordinator
      max_workers: 8                 # Thread pool for parallel queries
      description: >
        What this coordinator group covers.
        Used by the Lead for routing decisions.
      routing_prompt_extra: |
        How to route within this group.
        Which sub-agent handles what.

      agents:                          # Sub-agents within this group
        Agent_Root:
          repo_path: /path/to/repo
          model: claude-sonnet-4-20250514
          provider: anthropic
          description: >
            What files and topics this agent covers.
          key_files:
            - README.md
            - pyproject.toml
            - docs/
  • type: coordinator — Marks this as a group manager, not a leaf agent.
  • description — The Lead reads this to decide which coordinator to route to. Be specific and comprehensive.
  • routing_prompt_extra — The coordinator reads this to decide which sub-agent to route to within its group.
  • repo_path — Absolute path to the directory this agent reads files from.
  • key_files — List of files and directories the agent can see. Directories (ending with /) include all files within them.
  • model + provider — Each sub-agent can use a different model. This is how you get model diversity.
stack.yaml -- Twin pair pattern
      agents:
        Core_A:
          repo_path: /path/to/core
          model: claude-opus-4-6        # Model A: Anthropic
          provider: anthropic
          description: >
            Core business logic.
          key_files:
            - __init__.py
            - payments.py
            - storage.py
          twin: Core_B                  # Links to its twin

        Core_B:
          repo_path: /path/to/core       # SAME repo path as A
          model: grok-4-1-fast-reasoning # Model B: xAI (different!)
          provider: xai
          description: >
            Core business logic.        # Same description as A
          key_files:                    # Same key_files as A
            - __init__.py
            - payments.py
            - storage.py
          twin: Core_A                  # Links back (bidirectional)
Key rules for twin pairs
  • Both twins must have the twin field pointing at each other.
  • They should point at the same repo_path and have the same key_files.
  • They should have different models (ideally different providers) for genuine cognitive diversity.
  • Their descriptions should be identical — the coordinator needs to see them as interchangeable.
  • The top-level cross_pollination: true must be set for twins to activate.

Building Your Own Stack

Let us walk through creating a stack from scratch. The example use case: analyzing a legal contract from multiple expert perspectives.

Scenario
You have a SaaS company with three concerns: legal compliance, technical architecture, and business strategy. You want AI agents specialized in each area to analyze a contract, debate their findings, and produce a unified recommendation.

Step 1 — Define Your Coordinator Groups

Think about the distinct domains of expertise. Each domain becomes a coordinator group.

stacks/contract_review.yaml
name: contract-review

orchestration:
  mode: perspective
  max_iterations: 3
  cross_pollination: true

lead:
  model: claude-opus-4-6
  provider: anthropic
  routing_prompt_extra: |
    Three analysis groups:
    - **legal**: Regulatory compliance, liability, IP clauses
    - **technical**: Architecture impact, integration requirements
    - **business**: Financial terms, competitive positioning, risk

  keywords:
    legal:
      - compliance
      - liability
      - regulation
    technical:
      - api
      - integration
      - architecture
    business:
      - pricing
      - revenue
      - competition

Step 2 — Define Sub-Agents Within Each Group

Each coordinator group gets sub-agents. Point them at the relevant files. For contract review, each agent reads the contract plus domain-specific reference materials.

stacks/contract_review.yaml -- agents section
  agents:
    legal:
      type: coordinator
      description: Legal compliance and regulatory analysis
      agents:
        Legal_A:
          repo_path: /path/to/contracts
          model: claude-opus-4-6
          provider: anthropic
          description: Legal analysis of contract terms
          key_files:
            - contract.pdf
            - compliance_checklist.md
          twin: Legal_B

        Legal_B:
          repo_path: /path/to/contracts
          model: o4-mini
          provider: openai
          description: Legal analysis of contract terms
          key_files:
            - contract.pdf
            - compliance_checklist.md
          twin: Legal_A

Step 3 — Set Up Twin Pairs for Cognitive Diversity

For each twin pair, use different models and ideally different providers. This ensures the debate involves genuinely different reasoning architectures.

Twin PairModel AModel BWhy
Legal A / B Opus 4.6 o4-mini Deep vs. fast reasoning for legal nuance
Tech A / B Opus 4.6 Grok 4.1 Different architectures catch different edge cases
Biz A / B Sonnet 4 Gemini Flash Cost-effective for business analysis layer

Step 4 — Write Routing Instructions

The routing_prompt_extra on the lead is the most important text in your config. Be explicit about what each group handles and when to route to multiple groups.

Good routing instructions
  • Name each coordinator and list its scope
  • Define cross-cutting rules ("if question mentions both X and Y, route to both")
  • Specify default routing for ambiguous questions
  • Include example questions and where they should go

Step 5 — Choose Orchestration Mode

Use CaseRecommended ModeWhy
Quick factual lookupsstandardFast, cheap, one routing hop
Ambiguous technical questionsconsensusIdentifies contradictions, resolves them
Complex design / architecture tasksperspectiveFull multi-phase, highest quality

Step 6 — Run It

maz --config ./stacks/contract_review.yaml

API Key Setup

API keys are loaded from environment variables via a .env file in your project root. Each provider has its own variable. You only need keys for the providers you actually use in your stack.

.env
# Anthropic (Claude models)
ANTHROPIC_API_KEY=sk-ant-...

# OpenAI (GPT, o4-mini, etc.)
OPENAI_API_KEY=sk-...

# xAI (Grok models)
XAI_API_KEY=xai-...

# Google (Gemini models)
GOOGLE_API_KEY=AIza...

# Mistral (optional)
MISTRAL_API_KEY=...

# Cohere (optional)
COHERE_API_KEY=...

# NVIDIA (optional)
NVIDIA_API_KEY=nvapi-...

# Ollama (local, no key needed)
# OLLAMA_BASE_URL=http://localhost:11434/v1

Automatic provider detection
You do not need to specify base URLs for most providers. The framework infers the provider from the model name: claude-* maps to Anthropic, grok-* maps to xAI, gemini-* maps to Google, and so on. Just set the API key and use the model name in your YAML.

Running the System

Installation

pip install multiagentz[all]

# Or with specific providers only:
pip install multiagentz[anthropic]
pip install multiagentz[openai]

Launch

maz --config ./stacks/your_stack.yaml

This starts an interactive REPL. You type questions, the system routes them through your agent hierarchy, and you see the synthesized response in the terminal. Every response is also automatically exported to an HTML file in the ./outputs/ directory.

Understanding Terminal Output

While the system processes your question, you will see routing logs in the terminal:

[compression-buildout] Pre-route hint: nukez
[compression-buildout] Routing to: ['nukez']
[compression-buildout] Querying nukez...
  [nukez] Routing: Routes question about endpoint...

Each indentation level shows a different layer of the hierarchy. The top level is the LeadAgent, the second level is the coordinator, and the third level is the cross-pollination engine. This lets you see exactly how your question flows through the system.

Cost Awareness

Multi-agent systems use significantly more tokens than a single model. Understanding the cost multipliers helps you design stacks that balance quality against budget.

Cost Multipliers

  • Context size: Each agent ingests its key_files as context. Larger files = more input tokens per query.
  • Agent count: A question routed to 3 agents uses 3x the tokens of a single-agent query.
  • Cross-pollination: Twin pairs roughly double the per-cycle cost (parallel generation + swap/refine + reconciliation).
  • Iterations: Perspective mode with max_iterations: 5 can run up to 5 refinement cycles per perspective.
  • Bootstrap Q&A: Each Q&A turn in Phase 1 involves both perspective agents and the LEAD.

Cost Optimization

  • Start with max_iterations: 3 and only increase if quality is insufficient.
  • Use cheaper models for non-critical agents. Root/config agents that read READMEs and pyproject.toml files do not need Opus. Use Sonnet or Gemini Flash.
  • Reserve Opus for core logic agents where deep reasoning matters (complex business logic, security analysis).
  • Use standard mode for simple lookups and reserve perspective for complex design questions.
  • Keyword routing saves LLM calls. Good keyword coverage means the system skips the LLM routing classifier entirely for obvious questions.
  • The response cache avoids re-querying for similar questions within the TTL window.

Tips & Best Practices

Model Diversity Matters

Do not use all Opus models. The whole point of multi-agent systems is diverse reasoning. Mix providers: Anthropic + xAI + OpenAI + Google. Different architectures catch different blind spots.

Twin Pairs: Different Providers

When possible, use different providers for twin pairs (e.g., Opus + Grok). Same-provider twins (Opus 4.5 + Opus 4.6) still provide value through generational differences, but cross-provider pairs provide the strongest cognitive diversity.

Routing Instructions Are Everything

The routing_prompt_extra on your LeadAgent is the single most impactful configuration. Spend time writing clear, specific routing rules with examples. Bad routing means the best agents in the world get the wrong questions.

Start Small, Scale Up

Begin with 1-2 coordinator groups and 3-4 agents. Run some queries. See what works and what the system misroutes. Add agents as you discover blind spots. Do not start with 14 agents on day one.

Key Files Are Context Boundaries

An agent can only reason about what it sees. Be deliberate with key_files. An agent that sees everything produces generic answers. An agent that sees only routes/ becomes a genuine routing expert.

Use LEAD_SUB for Implementation

After the system produces a design recommendation, use /promote agent_name to promote the most relevant agent to LEAD_SUB. Subsequent questions route directly to it for detailed implementation, while architectural questions still go to LEAD.

Common Mistakes
  • Using the same model for everything. You are paying for a multi-agent system that thinks like a single model.
  • Vague routing instructions. "This handles backend stuff" is not good enough. List specific topics, file types, and cross-cutting rules.
  • Too many key_files. An agent that reads 50 files has enormous context and costs a lot. Be selective.
  • Skipping cross-pollination. Twin pairs are the highest-leverage feature. Use them for any agent that handles complex logic.
  • Setting max_iterations too high. After 3-5 iterations, returns diminish but cost keeps climbing. Start low.
